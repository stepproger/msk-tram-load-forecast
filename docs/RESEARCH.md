## 2. Как считаются баллы (39 максимум)

| Критерий | Баллы | Что реально даёт баллы | Цена |
|---|---|---|---|
| 1. WAPE-score | 0–10 | 0.48→2, 0.60→4, 0.70→6, 0.80→8, **>0.88→10** | высокая |
| 2. Данные и область применимости | 0–8 | 4 внешних источника × 1 (с **ссылкой** и **доказанным эффектом**) + 2 за описание области применимости + 1 за ползунки-коэффициенты в UI + 1 за воспроизводимый пайплайн | **низкая — самые дешёвые баллы** |
| 3. Архитектура и производительность | 0–5 | модули ingest→features→ML→API→UI, REST по (маршрут, остановка, интервал, горизонт), **замеры latency/RPS в README**, сервис запускается | средняя |
| 4. Полнота функциональности | 0–4 | день (обязательно) + месяц/год (хотя бы качественно), агрегация, карта, выгрузка CSV/XLSX | средняя |
| 5. Бизнес-ценность | 0–2 | применение к подвижному составу, переполнению, расписанию; честные ограничения | низкая |
| Питч полуфинала | 0–10 | глубина проработки (4), ответы жюри (3), выступление и демо (3) | средняя |

WAPE-score = max(0, 1 − Σ|y − ŷ| / Σy).

**Выводы:**
- Критерий 2 почти полностью «инженерный»: 8 баллов за источники, таблицу абляции и документ. Делать обязательно.
- WAPE считается по сумме, поэтому **ошибка на крупных значениях (часы пик, загруженные маршруты) весит больше всего**. Нули и хвосты почти не влияют.
- Если «сервис не запускается», баллы снижаются существенно. Docker Compose должен подниматься одной командой с первого дня.

## 3. ML-стратегия (уточнить после EDA)

### Что оптимизируем
- WAPE эквивалентен MAE, нормированному на сумму, поэтому модель должна прогнозировать **медиану**, а не среднее:
  LightGBM `objective='l1'` (или `huber`/`tweedie` — сравнить на валидации).
- После обучения подобрать глобальный множитель `k` (и, возможно, по маршрутам), минимизирующий WAPE на валидации. Дешёвый и частый прирост.
- Валидация должна **имитировать тестовый сплит** (такой же горизонт и тот же тип разбиения по времени). Иначе мы переобучимся на лидерборд.

### Лестница моделей (каждая ступень — сабмит)
1. Сезонная наивная: значение за тот же час и тот же день недели N недель назад, медиана по нескольким неделям. **Сабмит в первые часы**: проверим формат и сразу выйдем выше 0.48.
2. Иерархический профиль: маршрут × остановка × день недели × час, медиана и поправка на тренд.
3. LightGBM (L1) на признаках: календарь, профили-агрегаты (target encoding по маршрут/остановка/час/день недели), лаги **строго ≥ горизонта**, погода, праздники, каникулы, события.
4. Ансамбль LightGBM и профиля (+ CatBoost при наличии времени) и подбор множителя.

### Горизонты
- **День (обязательно, по часам)** — основная модель выше.
- **Месяц** — та же модель без коротких лагов (только календарь + профили + погода-климатология) или модель на дневных агрегатах.
- **Год** — дневная или месячная модель: тренд + годовая сезонность + календарь (Prophet-подобная декомпозиция или LightGBM на дневных суммах). Достаточно «качественно».
- Интервалы неопределённости (квантили 0.1/0.9 через LightGBM quantile) — сильный аргумент для диспетчеров и питча.

### Подводные камни
- Лаги ближе горизонта — утечка. На тест их не будет.
- Изменения маршрутной сети (ремонты путей, новые маршруты) ломают историю. Нужны флаги «маршрут не работал» и исключение аномальных периодов из обучения.
- COVID-2020/2021 (если история такая длинная) — исключить или пометить.
- Валидации — это **входы** пассажиров, а не наполняемость вагона. Наполняемость на участке требует оценки выходов (см. §6).

## 5. Архитектура (предложение)

```
[dataset.zip] ──► ml/ingest (Python, polars/duckdb) ──► data/processed/*.parquet
                                     │
[external APIs] ──► ml/external ─────┤
                                     ▼
                     ml/train (LightGBM) ──► artifacts/model.onnx + forecasts/*.parquet
                                     │
                                     ▼
backend (Java 21, Spring Boot 4.1, WebFlux/Netty)
  • при старте грузит предрасчитанные прогнозы в память (или ClickHouse/Postgres)
  • REST: /api/v1/forecast?route&stop&from&to&horizon&granularity
  • поправочные коэффициенты (погода/событие/сезон) применяются на лету
  • /api/v1/export?format=csv|xlsx
  • (stretch) ONNX Runtime в JVM для what-if по погоде
  • (stretch) SSE-поток «реального времени» — проигрывание истории/прогноза
                                     │
                                     ▼
frontend (React 19 + TS 5 + Leaflet + OpenStreetMap + ECharts/Recharts)
  • карта Москвы: остановки маршрута, цвет и размер = загрузка, ползунок времени с анимацией
  • графики по часам/дням, факт vs прогноз, интервалы
  • фильтры: маршрут, остановка/участок, интервал, горизонт
  • ползунки коэффициентов → прогноз пересчитывается сразу
  • кнопки CSV/XLSX
docker-compose: backend + frontend(nginx) [+ clickhouse/postgres]
```

**Почему предрасчёт:** требование «сотни RPS при p95 < 200–300 мс на 2–4 vCPU» выполняется тривиально, если backend отдаёт прогноз из памяти, а не гоняет модель на каждый запрос. Коэффициенты применяются как множители, поэтому пересчёт мгновенный. Нагрузочный тест — k6 или wrk, результаты в README (**обязательно**).

## 6. Бизнес-ценность и «вау» для питча

**Ответ организаторов (чат участников, 23.09):** упреждающие меры диспетчера — это
**(1) изменение количества ТС на линии** и **(2) изменение времени стоянки на остановках**.
Значит, прогноз в UI должен заканчиваться конкретной рекомендацией по этим двум рычагам:
- «Маршрут N, 08:00–09:00: нужно 14 вагонов вместо 11» (по прогнозу входов и вместимости);
- «Остановка X, пик 17–19: увеличить стоянку на +20 с» (по прогнозу входов на остановке: время посадки ≈ входы на рейс × сек/пассажира).

- **Индекс переполнения**: прогноз входов → оценка наполняемости на участке → доля от вместимости.
  Витязь-М (71-931М): 188 чел. номинально (5 чел/м²), 265 максимум (8 чел/м²), в Москве около 463 вагонов ([Википедия](https://ru.wikipedia.org/wiki/Витязь-М)).
  Оценка выходов: гравитационная модель или симметрия «утро туда — вечер обратно». Честно описать как допущение.
- **Рекомендация выпуска**: сколько вагонов в час нужно на маршруте, чтобы наполняемость была ≤ X%, против текущего расписания. Показывает переполнение и избыточные рейсы, то есть экономию.
- **Сценарии what-if**: ливень, праздник, матч в Лужниках → как меняется прогноз.
- **Прозрачность**: интервалы прогноза и объяснения признаков (SHAP top-факторы на маршрут).

## 7. Распределение работы

**Команда — 2 человека, каждый со своим агентом.** Пять треков ниже сводятся к двум зонам ответственности:
- **Человек 1 — «Данные и модель»**: треки A + B (Python, `ml/`, `data/`). Критичный путь к 10 баллам за WAPE и 8 за данные.
- **Человек 2 — «Продукт»**: треки C + D (+ сборка Docker) (`backend/`, `frontend/`, `infra/`).
- Трек E (документы, питч) агенты ведут по ходу работы. Каждый дописывает свою часть в `docs/`, финальную сборку README делает Человек 2 вечером 27.09.

Правило: **сначала контракты, потом параллель**. Каждый владеет своей папкой, пересечения только через файлы контрактов в `docs/contracts/`.

| Трек | Папка | Роль | Зависит от |
|---|---|---|---|
| A. ML-прогноз и сабмиты | `ml/` | ML-1 | EDA, контракт данных |
| B. Данные: ingest, внешние источники, абляции | `ml/ingest`, `ml/external`, `data/external` | ML-2 / DS | EDA |
| C. Backend API + нагрузочный тест + Docker | `backend/`, `infra/` | Backend | контракт API, формат прогнозов |
| D. Frontend-дашборд | `frontend/` | Frontend | контракт API (работает на моках с первого часа) |
| E. Документы, архитектура, питч, бизнес-метрики | `docs/`, `pitch/` | Аналитик/PM | всё, но стартует сразу |

Контракты, которые фиксируем **до** параллельной работы:
1. `docs/contracts/data_schema.md` — нормализованная таблица фактов (route_id, stop_id, ts_hour, value, …) и справочник остановок с координатами.
2. `docs/contracts/forecast_schema.md` — формат предрасчитанных прогнозов (route, stop, ts, horizon, yhat, q10, q90, model_version).
3. `docs/contracts/openapi.yaml` — REST API. Frontend генерирует типы и моки из него.
